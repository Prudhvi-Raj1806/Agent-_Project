# JARVIS Master Memory Capsule

Durable architectural and product decisions. This document changes rarely — only when a real decision is made, not every time code changes. For "what's actually built right now," see `JARVIS_CURRENT_STAGE.md`. For phase-by-phase status, see `JARVIS_PHASE_STATUS.md`.

## North Star

JARVIS is a persistent personal AI operating environment, not a chatbot with tools. JARVIS (this codebase) governs: identity, policy, permissions, world state, memory, events, verification, mission lifecycle. Hermes (a separate, external agent runtime) reasons, plans, and executes. Tools provide capabilities. Electron comes last — the system must stay architecturally independent of any desktop shell until the core is functionally complete.

## Module boundaries (as actually drawn in code)

- `src/server/missions` — the mission runtime: lifecycle state machine, persistence, orchestration pipeline. The orchestrator (`orchestrator.ts`) is the *only* module that drives a mission's status beyond direct user commands. `missions/tasks` (task-DAG foundation) and `missions/checkpoints` (real checkpoint records) are sub-modules with their own tables, mirroring the same repository/service split as the parent. Every pipeline execution (`executePipeline`, started from `beginMission`/`resumeMission`) carries a run-generation number (`startNewRun`/`isStaleRun` in `orchestrator.ts`, added 2026-09-21): only the current generation for a mission may mutate its state, so a paused run that resolves late (after a resume already started a newer run) is detected and discarded rather than stomping the newer run's outcome. `pauseMission`/`cancelMission` also invalidate the current generation outright, so a stale run is rejected even before any resume. Do not remove this in favor of relying on `AbortSignal.aborted` alone — that was the pre-2026-09-21 approach and is exactly what let the race through (an adapter that doesn't turn abort into a prompt rejection could still resolve successfully). `missions/completion-policy.ts` (`decideMissionCompletion`, Production Sprint 03, 2026-09-21) is the *only* function allowed to decide COMPLETED vs. FAILED from a `VerificationResult` — see the standing invariant below; `orchestrator.ts`'s final block calls it rather than branching on the verdict inline.
- `src/server/tools` — the Tool Registry and the canonical side-effect execution boundary (Phase 04, initial slice added 2026-09-21, extended into the single governed boundary in Production Sprint 02, same day): `types.ts` (the `ToolDefinition` shape — id, description, risk, capabilities, permission, inputSchema, sideEffects, verificationStrategy, optional `verify`), `registry.ts` (built from `src/server/actions/registry.ts`'s `ACTION_REGISTRY` — Quick Actions are today's only registered, JARVIS-executed tools), `executor.ts`, `verification.ts` (Production Sprint 03, same day). `executor.ts` exports `executeTool` (Quick Actions — JARVIS executes the tool itself via a `ToolDefinition.execute()`: Request → Tool Registry → Policy → Permission → Execution → Audit) and `evaluateGovernedToolCall`/`recordToolCallResolution` (the shared policy-evaluation-and-audit primitives both `executeTool` *and* `missions/orchestrator.ts`'s `handleToolRequest` call — see the invariant below). `verification.ts`'s `verifyToolOutcome` is deliberately **not** part of `executor.ts` — ToolExecutor stays execution-only; observation/verification is a separate step, called by `src/server/actions/service.ts`'s `runQuickAction` (a thin wrapper around `executeTool`, now followed by a `verifyToolOutcome` call) after execution completes. **Important distinction, not a gap:** Hermes-mediated tool calls (`read_file`, `write_file`, ...) are not — and will not be — added as `ToolDefinition` registry entries with a local `execute()`, because JARVIS does not execute them; Hermes's own runtime does (Hermes is the intelligence/execution runtime, not the security boundary). For that surface, "governed by ToolExecutor" means the ALLOW/ASK/DENY policy decision and its audit record are produced by `tools/executor.ts`, not that JARVIS locally runs the tool.
- `src/server/providers` — the provider abstraction beneath OmniRouter's routing decision, added 2026-09-21 (`completion.ts`): `runProviderCompletion(routing, prompt)` is the one place a one-shot text completion (as opposed to a full Hermes mission) is actually executed against a model provider's API. Only Anthropic has a real implementation; every other OmniRouter-seeded provider honestly returns "not implemented" rather than fabricating a result. No application code outside this module may call a model provider's API directly — `src/server/actions/registry.ts`'s `summarize-clipboard` action used to violate this (a hardcoded `fetch` to `api.anthropic.com` with a hardcoded, since-stale model string) and has been moved onto this abstraction.
- `src/server/hermes` — the intelligence boundary. One `HermesAdapter` interface, three implementations (mock / generic HTTP / Hermes-Agent-specific) selected by env var at `factory.ts`. JARVIS never embeds Hermes's reasoning; it only defines the contract Hermes must speak. As of 2026-09-21, the Hermes-Agent-specific adapter (`agent-adapter.ts`) has been verified against a real, locally-running Hermes Agent (github.com/NousResearch/hermes-agent v0.21.0) — see JARVIS_CURRENT_STAGE.md for what "real" means here and how to bring that runtime up. As of Production Sprint 06 (2026-09-22), `agent-adapter.ts` also forwards Hermes's real `tool.started`/`tool.completed` SSE frames through `HermesExecuteCallbacks.onToolEvent` — the same generic observation channel `http-adapter.ts` already used, previously never wired up for the real adapter. This is a second, distinct signal from `onToolRequest`/`approval.request`: it is unconditional (fires for every tool call, gated or not) but non-blocking (Hermes does not wait for a response), so it gives JARVIS genuine post-hoc/concurrent *observability* of Hermes's tool calls, not pre-execution *control* of them — see the Hermes capability-boundary section below for why that distinction is load-bearing.
- `src/server/omnirouter` — model/provider routing metadata and selection *reasoning* (regex-classified objective → provider/model), not model execution itself. It gates whether a mission may run at all (no healthy provider → mission fails) and records an audit trail; it does not call any model API directly. Note: this is JARVIS's own internal routing/audit layer and is separate from the real third-party `omniroute` CLI gateway Hermes Agent is configured to route its actual model calls through — same name, different systems; do not conflate them.
- `src/server/events` — the event bus: single write path (`emitEvent`), persisted to SQLite and published to an in-process `EventEmitter`, consumed live via SSE.
- `src/server/world-state` — Phase 03's reconciliation layer, added 2026-09-21. `getWorldState()` queries all domain services (system, missions, files, spotify, schedule, weather, news, omnirouter, hermes) in parallel and wraps each in `{data, fetchedAt, knownCacheTtlMs, error}`. It does not replace `events` (the append-only history/audit log) or any domain's own service (still the source of truth, still owns its own caching) — it is a read-through aggregator only, with no caching or polling of its own. A domain failing (e.g. Spotify not connected) never fails the rest of the snapshot.
- `src/server/security` — policy (mission-creation-time) + tool-policy (execution-time gate) + audit. Deliberately fail-closed: unknown tool names are treated as high-risk `ASK`, not silently allowed; a missing tool-request handler denies by default; as of Production Sprint 04 (2026-09-21), a thrown error *during* policy evaluation itself is also caught and converted to an explicit, audited DENY inside `tools/executor.ts`'s `evaluateGovernedToolCall`, rather than relying on the exception happening to prevent execution as an accidental side effect. `tool-policy.ts`'s `evaluateToolRequest`/`DEFAULT_TOOL_RULES` is shared by *both* Hermes tool calls and Quick Actions (a Quick Action's id is just another `toolName`) — this is the one execution-time security boundary for anything JARVIS can be asked to run, not a mission-only concern. As of Production Sprint 02 (2026-09-21), `evaluateToolRequest` is called from exactly one place in application code — `tools/executor.ts`'s `evaluateGovernedToolCall` — not from two independent call sites; see the standing invariant below. This single-call-site property has a repository-wide structural regression test as of Production Sprint 04 (`security/governed-boundary.test.ts`), not just the one file-scoped behavioral test Sprint 02 added — it scans all of `src/` and fails if `evaluateToolRequest` is ever imported by name from anywhere in non-test application code other than `tools/executor.ts` (the gate) or `tools/registry.ts` (a single documented exception — reads a tool's `risk` for registry metadata only, never gates execution; see that file's own comment). `audit.ts`'s append-only guarantee is DB-enforced as of Production Sprint 04 (two SQLite triggers on `audit_events` in `db/schema.ts` that abort any UPDATE/DELETE), not merely an application convention — though this defends the ordinary application-code path only, not raw filesystem tampering or a future migration removing the triggers.
- `src/server/verification` — deterministic, non-LLM verdicts. A floor, not a ceiling: it can never mistake "the model responded" for "the mission succeeded." `verifier.ts` is the pre-existing text-match strategy for Hermes missions (unchanged in behavior, now tags its results `strategy: "text-match"`). `classification.ts` (Production Sprint 03) is a minimal, deterministic failure taxonomy (`TRANSIENT`/`PERMANENT`/`POLICY_DENIED`/`PERMISSION_DENIED`/`VERIFICATION_FAILED`/`VERIFICATION_UNCERTAIN`/`UNKNOWN`) — every classifier returns `UNKNOWN` rather than guessing when the evidence doesn't clearly support a more specific category; this is metadata attached to failure events, not a retry engine. `execution-identity.ts` is a stable-key builder (`missionId`/`taskId`/`toolCallId`) for a *future* retry/idempotency system — it names executions, it does not suppress or dedupe them.
- `src/server/db` — the only code that touches SQL. `node:sqlite` (`DatabaseSync`), one local file, WAL mode, foreign keys on. Repository modules elsewhere are the only other code allowed to import `getDb()`.

## Standing invariants (do not silently violate these)

1. **Honesty Rule is enforced in code, not just policy.** The mock Hermes adapter labels every result `source: "mock"` and puts "MOCK HERMES — no real agent runtime connected" directly in the output text. The verifier can never return `PASS` when a mission declares zero success criteria. OmniRouter's per-model usage is always `[]` rather than a fabricated percentage when no real provider telemetry exists. Any new subsystem must follow this pattern: an honest empty/unknown state, never a plausible-looking fake one.
2. **Fail-closed on tools JARVIS actually sees.** High/critical-risk tools never auto-allow, even if pre-approved in `allowedTools`. Unrecognized tool names default to `ASK`, not `ALLOW`. No tool-request handler configured → deny. A thrown error during policy evaluation itself also fails closed to an audited DENY as of Production Sprint 04, rather than relying on the exception's incidental control-flow effect. **Important caveat, confirmed by live testing 2026-09-21, re-confirmed by code inspection 2026-09-21 (Production Sprint 04), and root-caused with source evidence 2026-09-22 (Production Sprint 06):** this only covers tool calls the connected Hermes runtime actually reports via a `tool.requested`/`approval.request` frame. The real Hermes Agent integration does *not* report every tool call it makes this way — live testing across read, write, AND shell-command categories (Production Sprint 06) all produced zero `tool.requested` events. The root cause is now known, not just observed: Hermes Agent has no per-tool risk classification at all (approval is command/path pattern matching, not a tool-name property), and its `api_server` platform is **hardcoded** into an unattended-approval context (`tools/approval_context.py`'s `_UNATTENDED_APPROVAL_PLATFORMS` frozenset, in Hermes's own installed Python source — not a config value) that bypasses the interactive round-trip almost entirely. **This specific mechanism is not fixable by JARVIS-side configuration, and was not fixed** — modifying Hermes's installed source is out of scope for every sprint's rules. What Production Sprint 06 *did* find and fix: Hermes's api_server also emits a second, unconditional `tool.started`/`tool.completed` event pair for every tool call regardless of approval status — genuinely useful, previously unconsumed by `hermes/agent-adapter.ts` (its `stream()` method only ever invoked `callbacks.onToolRequest`, the governed gate, from its `"approval.request"` case; the other frame types fell into a silent no-op default). `agent-adapter.ts` now forwards these through the pre-existing `HermesExecuteCallbacks.onToolEvent` observation channel, verified live end-to-end. **This closes JARVIS's visibility gap, not its governance gap — do not conflate the two.** JARVIS can now audit, after or concurrently with the fact, every read/write/shell-command tool call Hermes Agent makes via api_server (tool name, an argument preview, duration, success/failure) — genuinely observed, not fabricated. It still cannot allow/ask/deny a call Hermes's own approval system doesn't already choose to flag via `approval.request`, because `tool.started` does not pause Hermes for a response the way `approval.request` does — there is no channel to answer it through. Do not describe or rely on JARVIS's tool gate as covering "everything Hermes does" — it covers "everything Hermes chooses to ask about," now paired with an audit trail of "everything Hermes actually did," which is a real improvement but not the same thing. Do not attempt a partial/speculative sandbox to "look closed" — an honest open gap is preferable to an invented guarantee (see standing invariant #1). See the Hermes capability-boundary section below and JARVIS_PHASE_STATUS.md Phase 02/05/07 for the full picture and the Planner-blocking consequence.
3. **`emitEvent()` is the only way to create an event.** Never insert into the `events` table directly, and never mutate mission/task state without also emitting the corresponding event — the SSE stream and history replay depend on this being true for every state change.
4. **New DB tables need no migration entry; altering an existing table does.** `CREATE TABLE IF NOT EXISTS` in `SCHEMA_SQL` is sufficient for anything new. Only `ALTER TABLE` against a table that has already shipped goes in the `MIGRATIONS` array (and must tolerate re-running against a DB that already has the column).
5. **SQLite is the local single-user world-state store by design, not a placeholder.** Structured columns are JSON `TEXT` specifically so a future move to Postgres/JSONB only touches the repository layer, not services or callers.
6. **Dark theme is not a setting.** `<html className="dark">` is hardcoded in `layout.tsx` — JARVIS has one visual identity, not a light/dark toggle.
7. **Never fabricate multi-step intelligence ahead of the phase that earns it.** When a subsystem's DAG/graph/plan shape is built before the reasoning to fill it exists (e.g. the Phase 01 task model before Phase 07's planner), the code must create the minimal honest structure (e.g. exactly one root node) and say so in a comment — not synthesize fake decomposition to make the feature look more capable than it is.
8. **A budget dimension that can't be honestly enforced stays unenforced, not approximated.** `Mission.budget.maxUsd` has no real cost figure to check against anywhere in the system (Hermes Agent's `usage` object reports tokens, not `cost_usd`, on the terminal event JARVIS actually consumes) — it is accepted and stored, never checked, and this is documented, not silently ignored. Contrast with `maxTokens`, which real usage data now exists for and is genuinely enforced (post-hoc, since Hermes only reports totals at completion — see `orchestrator.ts`'s `failMissionOnBudgetViolation`).
9. **A schema-only field superseded by a real table stays as dead schema, not a second write path.** `Mission.checkpoints` (JSON column) predates `missions/checkpoints` (a real dedicated table + repository + service, added 2026-09-21, same pattern as `mission_tasks`) and is never written to by any code — the table is canonical. Do not "fix" this by writing to both; query checkpoints via `listMissionCheckpoints(missionId)`, not `mission.checkpoints`.
10. **No application surface calls `ACTION_REGISTRY[id].run()` (or any provider API) directly — every execution goes through a policy/audit boundary first.** Before 2026-09-21, the Quick Action API route called `ACTION_REGISTRY[id].run()` directly (a second, ungated execution path next to the mission pipeline's `handleToolRequest` gate), and `summarize-clipboard` called `api.anthropic.com` directly with a hardcoded model. Both are closed: Quick Actions now run through `src/server/tools/executor.ts`'s `executeTool` (policy-evaluated and audited via the same `tool-policy.ts`/`audit.ts` missions use), and `summarize-clipboard` routes through `src/server/providers/completion.ts`. Do not reintroduce a direct call to `ACTION_REGISTRY`'s `run()` or a provider's raw API from anywhere outside these two modules.
11. **Tool execution success and requested-outcome success are separate concepts — JARVIS must not report verified success unless sufficient evidence establishes the requested success criteria.** (Production Sprint 03, 2026-09-21.) "Hermes reported success" / "the tool returned `{ok: true}`" is never, on its own, "the mission achieved what it was asked to achieve." Concretely: `missions/completion-policy.ts`'s `decideMissionCompletion` is the *only* function allowed to decide a mission's COMPLETED/FAILED outcome from a `VerificationResult`, and it enforces: verdict `FAIL` → `FAILED`; verdict `UNCERTAIN` with success criteria declared → `FAILED` (evidence was insufficient to call this verified — do not let it silently become `COMPLETED`, and never reinterpret `UNCERTAIN` as `PASS`); verdict `UNCERTAIN` with no criteria declared → `COMPLETED` (the one deliberate exception — a mission that never asked to be verified never failed to verify). At the tool level, `tools/verification.ts`'s `verifyToolOutcome` never wraps a tool's bare self-report in the same `VerificationResult` shape a real observation produces (it returns `null` for a "self-reported" tool instead) — a self-report and an independent observation must never look identical to a caller. When evidence is insufficient, verification returns `UNCERTAIN` rather than `PASS`, in both the mission and tool layers. Do not add an LLM-based "does this look successful?" verifier — the deterministic floor (text-match, self-reported, file-exists) is what exists today; semantic/independent verification is a later, explicitly separate increment (Phase 06).
12. **`tools/executor.ts` is the one place `security/tool-policy.ts`'s `evaluateToolRequest` is called from application code — every tool request is policy-evaluated and audited through it, whether JARVIS executes the tool itself or not.** Fixed in Production Sprint 02 (2026-09-21): before this, `missions/orchestrator.ts`'s `handleToolRequest` (the gate for every Hermes-mediated tool call) called `evaluateToolRequest` and `recordAudit` directly, inline — a second, independent call site next to `executeTool`'s (Quick Actions). Both now go through `executor.ts`'s `evaluateGovernedToolCall` (policy evaluation + audit for an immediate ALLOW/DENY verdict) and `recordToolCallResolution` (audit for an ASK verdict's eventual approval/denial — a voice-verification token for Quick Actions, a human resolving a mission's `WAITING_USER` wait for Hermes calls). This does **not** mean Hermes's tools (`read_file`, `write_file`, ...) become `ToolDefinition` registry entries with a local `execute()` — JARVIS never executes them; Hermes's own runtime does. "Governed by ToolExecutor" for that surface means the ALLOW/ASK/DENY decision and its audit record are produced by `tools/executor.ts`, not that a local handler runs. `src/server/missions/tool-request-boundary.test.ts` structurally proves this by mocking `tools/executor.ts` out and asserting the real `security/tool-policy.ts`'s `evaluateToolRequest` is never called directly by the orchestrator. `src/server/security/governed-boundary.test.ts` (Production Sprint 04) proves the same property repository-wide, by static source scan rather than one file's behavior — the only non-test application exception is `tools/registry.ts`'s single, metadata-only read of a tool's `risk` (never a gate). Do not reintroduce a direct `evaluateToolRequest`/`recordAudit` call pair from `missions/orchestrator.ts` (or any future tool-executing surface) — route it through `tools/executor.ts` instead.
13. **`audit_events` is append-only at the database level, not merely by application convention.** (Production Sprint 04, 2026-09-21.) `db/schema.ts` defines `audit_events_no_update`/`audit_events_no_delete` triggers that `RAISE(ABORT, ...)` on any `UPDATE`/`DELETE` against the table — proven by `security/audit.test.ts` issuing a direct SQL statement against the table, bypassing `recordAudit` entirely. Stated precisely: this closes the ordinary application-code path (no service, route, or future feature can silently rewrite history through `getDb()`), not raw `.sqlite` file tampering or a migration that drops the triggers — do not describe this as cryptographic tamper-evidence, it isn't one.
14. **Secret redaction in logs is value-based as well as field-name-based.** (Production Sprint 04, 2026-09-21.) `logging/logger.ts`'s pre-existing field-name redaction (`SECRET_KEY_PATTERN` on the object key) left a real gap: a genuine secret value logged under an unrelated key, or embedded as a substring inside a longer string (e.g. an error message containing a token), passed through unredacted. `redact()` now also scans every logged string for exact occurrences of any currently-configured value from a fixed, known list of secret-shaped env vars this codebase actually reads (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `DEEPSEEK_API_KEY`, `OMNIROUTE_API_KEY`, `HERMES_AGENT_API_KEY`, `ELEVENLABS_API_KEY`, `JARVIS_VOICE_PASSCODE`, `SPOTIFY_CLIENT_SECRET` — the set `.env.example` documents), independent of field name; values under 8 characters are skipped as too short to reliably identify as secrets. This is a real, narrow mitigation, not a secret vault — `.env.local` still holds plaintext secrets on disk, and this only prevents them from additionally leaking into structured logs. Do not read this as "secrets are now safe everywhere" — it closes exactly the gap the prior audit named (log redaction), nothing more.
15. **Owner-direct UI side effects with no agentic/Hermes-reachable path are a different trust category than Quick Actions or Hermes tool calls, and are not automatically brought under the Tool Registry.** (Documented, Production Sprint 04, 2026-09-21 — a finding, not a fix.) Spotify's playback-control routes (`/api/spotify/play`/`pause`/`next`/`previous`/`volume`/`seek`/`transfer`) call the real Spotify API and are genuine external side effects, but are not registered in `DEFAULT_TOOL_RULES` and do not run through `tools/executor.ts` — unlike Quick Actions, which were brought under the registry in Production Sprint 01 specifically because they had *both* an owner-direct route and (potentially) a Hermes-mediated path to the same class of action. No tool name for media control exists today, so Hermes cannot reach these routes at all; they are scoped entirely to what the owner's own already-consented Spotify OAuth grant allows. This is a real, standing architectural gap worth a deliberate decision if Hermes or any future agentic surface ever gains a reason to control media — not an oversight to silently fix, and not urgent while no such path exists.

## Product/UI decisions

- Home Mode, Work Mode, Focus Mode, Music, System, IMA (news feed), Calendar, and Settings are sibling routes under one shared `AppShell` (sidebar + top bar) — not nested mode-switch layouts. Home is the ambient/glanceable surface; Work is the operational surface (missions, OmniRouter, tasks, focus tools).
- Visual direction: premium, restrained, dark, functional, minimal, developer-grade. No cyberpunk HUD, no giant glowing orb, no decorative graphs, no fabricated metrics. An empty/offline state (e.g. "No active missions," a provider shown OFFLINE) is correct UI, not a bug to hide.
- Frontend priority order for Work Mode (per the roadmap): Command Bar → mission creation → Mission Inspector → live SSE updates → mission controls → real event stream → real OmniRouter state → dedicated operational screens. As of this writing, all of these are implemented and wired to real backends (verified: Command Bar POSTs to `/api/missions`; OmniRouter panel reflects real provider online/offline state; missions are consumed live via SSE, not polling).

## Naming conventions worth preserving

- ID prefixes are per-domain and must not collide: `mission`, `task` (personal to-do items — unrelated to mission tasks), `mtask` (mission-task-DAG nodes), `chk` (mission checkpoints), `sched`, `audit`, `evt`.
- `src/server/tasks/` (personal to-do list) and `src/server/missions/tasks/` (mission task DAG) are deliberately separate, differently-scoped concepts that happen to share the word "task" — do not merge them or rename one to make the collision go away; the subdirectory nesting under `missions/` is what disambiguates the import path.

## Local real-infrastructure dependencies (2026-09-21)

Two real third-party processes must be running locally for JARVIS to use its real (non-mock) Hermes path — both genuinely installed on this machine, not something JARVIS's own code manages:

1. **OmniRoute gateway** (`omniroute serve`, port 20128) — the real model-routing gateway Hermes Agent calls into. Start/stop/check via the `omniroute` CLI (`serve` / `stop` / `health`). Takes ~20-25s to fully report healthy after starting — a health check run immediately after start can read as unhealthy while it's still warming up.
2. **Hermes Agent gateway** (`hermes gateway run`, port 8642) — the real agent runtime, via its `api_server` platform. Depends on (1) being up first (its configured model provider is OmniRoute). Config already set up (`hermes config set platforms.api_server.*`, `API_SERVER_KEY` in its own env file, matching `HERMES_AGENT_API_KEY` in this repo's `.env.local`) — see `.env.example` for the exact commands if it ever needs re-doing on a fresh machine.

Neither is started automatically by `npm run dev` — they are separate, standing processes. If `GET /api/hermes/health` reports `healthy: false`, check whether these are running before assuming a code regression.

## Hermes capability boundary (Production Sprint 06, 2026-09-22)

Durable architectural conclusion from a source-and-live-evidence investigation into what Hermes Agent (v0.21.0, via its `api_server` platform) can do independently of JARVIS, and whether that's configurable. Full experiment log, raw-wire evidence, and the fix this sprint shipped are in JARVIS_CURRENT_STAGE.md's Production Sprint 06 section — this section is the standing conclusion, not the investigation log.

**How Hermes actually decides what needs approval (REAL, source-verified):** there is no per-tool risk classification in Hermes's tool registry. Approval is command-string/path pattern matching: `DANGEROUS_PATTERNS`/`HARDLINE_PATTERNS` regexes for shell commands, a narrow sensitive-path allowlist for file writes. Everything else — including ordinary reads, ordinary writes, and ordinary shell commands, confirmed by live test — executes with no approval check of any kind. The `api_server` platform is additionally **hardcoded** (not configurable) into an unattended-approval context that bypasses even that pattern-matching's interactive round-trip for anything it does flag.

**Capability table (REAL = verified live this sprint; SOURCE-VERIFIED = read from Hermes's own installed code, not live-tested; UNVERIFIED = not checked):**

| Capability | Owner | Read-only | Side effect | JARVIS pre-execution control | JARVIS observability (post Sprint 06 fix) | Evidence |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| file listing / search (`search_files`) | Hermes | yes | no | No | Yes (`tool.started`/`tool.completed`) | REAL — live test + raw SSE capture |
| file read | Hermes | yes | no | No | Yes (same path; same tool category) | REAL |
| file write (ordinary path) | Hermes | no | yes | No | Yes | REAL — live test, file genuinely created, zero gate events |
| file write (sensitive path, e.g. `~/.ssh/config`) | Hermes | no | yes | Only via Hermes's own internal gate, never JARVIS's | Unknown whether `tool.started` still fires when Hermes's own gate blocks it | SOURCE-VERIFIED (gate exists); UNVERIFIED (interaction with the new observability path) |
| shell command (not matching Hermes's dangerous-pattern list) | Hermes | no | yes | No | Yes | REAL — live test (`date`), zero gate events |

**Trust boundary:**
- **JARVIS's authority:** mission-creation-time policy; the execution-time ALLOW/ASK/DENY gate (`security/tool-policy.ts`, reached only via `tools/executor.ts`, only for calls Hermes chooses to report as `approval.request`); the append-only audit log; verification of declared success criteria; budget enforcement; and, as of this sprint, passive observation of every tested category of Hermes tool call.
- **Hermes's authority:** virtually all tool-selection and execution decisions for api_server-driven missions. Its own hardcoded, pattern-matching approval system is the *only* pre-execution gate that ever applies — JARVIS's own `DEFAULT_TOOL_RULES` risk table is simply never consulted unless Hermes's system independently chooses to ask.
- **JARVIS-visible (post-fix):** every tool call in the three tested categories (read/write/shell), genuinely, via `tool.started`/`tool.completed`.
- **Still fully outside JARVIS's pre-execution reach:** everything not matching Hermes's own dangerous-command patterns or sensitive-write-path list — per live evidence, this includes ordinary writes and ordinary shell commands, not only reads.
- **Configurable but not yet applied:** `command_allowlist` and `approvals.deny` (real, `fnmatch`-glob, unconditional-before-auto-approve mechanisms on the Hermes side) could tighten the shell-command surface specifically, without needing any new JARVIS infrastructure — this installation's `config.yaml` has neither set.
- **Not configurable at all:** api_server's exclusion from Hermes's interactive-approval context (`_UNATTENDED_APPROVAL_PLATFORMS`) is a hardcoded set in Hermes's own installed source, not a config key.

**Planner/Replanner consequence (see also JARVIS_PHASE_STATUS.md Phase 07):** BLOCKED. Visibility is necessary but not sufficient for safe delegation. A Planner that hands a mission to Hermes today would be delegating to a runtime that can independently read, write, and run shell commands with no JARVIS-side pre-execution governance for any of those categories in this installation — JARVIS would only ever find out afterward, via the observation path this sprint added. Two concrete, non-speculative paths would unblock this, neither requiring a new sandbox: (1) configure Hermes's own `command_allowlist`/`approvals.deny`/`unattended_mode` to mirror JARVIS's `DEFAULT_TOOL_RULES` risk taxonomy, accepting that the enforcement point lives in Hermes's config rather than JARVIS's code; or (2) scope Planner's own autonomy to what JARVIS can actually govern today (e.g., read-only/low-risk objectives only, or mandatory human-in-the-loop before a mission that might need Hermes to write or execute). Do not start Planner on the assumption that this sprint's observability fix closed the governance gap — it did not, by design (see standing invariant #2).

## Hermes capability governance — the (1) path actually tried (Production Sprint 07, 2026-09-22)

Sprint 06 left one open question: is the "tighten `command_allowlist`/`approvals.deny`/`unattended_mode`" unblocking path in the section above real, or just plausible from source? Sprint 07 tried it — controlled experiments, evidence-recorded, no Hermes source or installed-dependency changes, no destructive commands. Full experiment log (exact commands, exact results) is in JARVIS_CURRENT_STAGE.md's Production Sprint 07 section; this is the standing conclusion.

**Method note (an honest environmental limitation, not a shortcut):** this installation's configured model backend (a local `antigravity`/OmniRoute proxy at `127.0.0.1:20128`) was unreachable this session (`httpcore.ConnectError`, confirmed in Hermes's own gateway log) — bringing the real `api_server` gateway up and submitting a mission produced `run.failed`/`Connection error.` for every attempt, before Hermes's own model ever got far enough to decide on a tool call. A live, LLM-driven, full-SSE-wire reproduction of Sprint 06's method was therefore not possible this session. Instead, Sprint 07 imported Hermes's own installed `tools.approval`/`tools.approval_context` modules directly (via Hermes's own bundled venv Python, `hermes-agent/venv/Scripts/python.exe`) and called `check_all_command_guards`/`check_execute_code_guard` — the exact functions `tools/terminal_tool.py` calls before executing anything — as a library, in-process, with `HERMES_SESSION_PLATFORM=api_server` set to reproduce the real unattended context. No config.yaml write, no subprocess actually executed (these functions only return an approve/deny verdict — `terminal_tool.py:843-844` shows the caller `raise`s before spawning anything when `approved` is false, confirmed by reading that call site, so a verdict of `approved: False` here is genuinely "never executes," not just "logs a warning"). `command_allowlist`/`approvals.deny` cases were seeded/monkeypatched into that one process's memory only, never written to the operator's real `config.yaml`.

**Findings (all live, this sprint, against Hermes's real installed 0.21.0 code — not simulated):**
- **`command_allowlist` is a bypass, not a restriction.** It is the mechanism behind "always allow this exact command" — matched commands skip straight to `_approved()`, silently, even under `api_server`. It has no denylist mode and cannot be used to restrict Hermes to *only* running listed commands; everything not on the dangerous-pattern list already runs unlisted and ungated regardless of what's in it. Live-confirmed: a command that Hermes's own detector already flags as dangerous (a PowerShell `Remove-Item ... -Recurse -Force`) is genuinely blocked under this installation's default config (`unattended_mode: deny`), and genuinely un-blocked the instant that exact command string is added to `command_allowlist` — a different dangerous command not on the list stays blocked, confirming the match is exact/glob-specific, not a blanket toggle.
- **`approvals.deny` is a real, unconditional hard block, independent of and senior to `command_allowlist`.** A command matching an `approvals.deny` glob was blocked live even though it did **not** match any of Hermes's own built-in dangerous patterns (i.e., it's an operator-extensible denylist, not just a stricter view of the built-in one) — and stayed blocked after the *same* command was also added to `command_allowlist`, live-confirming the source comment ("never bypassable... not by yolo") extends to the allowlist too, not only to yolo/`mode: off`.
- **`unattended_mode: deny` (the live default; this installation has no `approvals:` block at all, so every value in this section is Hermes's own out-of-the-box default, not anything JARVIS's operator configured) already blocks every dangerous-pattern-matched shell command under `api_server` today**, with no configuration needed — this was previously only source-verified (Sprint 06 declined to test it live, correctly, given the destructive-command risk); Sprint 07's in-process method made testing it live safe (the gate function never spawns a process) and confirms the default is doing real work, not sitting inert.
- **`execute_code` is fully blocked under `api_server` by the same default, resolved from UNVERIFIED to REAL.** Sprint 06 flagged this row UNVERIFIED. Live-confirmed this sprint: with no config changes, an `execute_code` call under the `api_server` context returns `approved: False` unconditionally (a whole-script gate, not per-line) — the single best-governed capability Hermes exposes today, purely from its shipped default.
- **Everything Sprint 06 already found ungated stays ungated — re-confirmed, not just assumed:** ordinary (non-pattern-matched) shell commands and ordinary file writes still return `approved: True` with zero gate interaction under this same live-default configuration; `tools/web_tools.py`'s `web_search_tool` (checked fresh this sprint — not examined in Sprint 06) has **no approval call anywhere in the file** — network access is exactly as ungated as ordinary writes, not merely unverified.

**Capability matrix (REAL = this sprint's live in-process evidence or Sprint 06's live SSE evidence; SOURCE-VERIFIED = read from Hermes's installed code, not executed; below "Hard block possible" means Hermes itself can refuse the call before it runs — not that JARVIS causes the refusal):**

| --- | --- | --- | --- | --- | --- | --- |
| Reasoning / planning | N/A | N/A | N/A | Yes (`message.delta` → progress) | N/A | No |

**Governance decision: PARTIALLY GOVERNED.** Hermes's existing, supported configuration *does* provide a real, live-confirmed, pre-execution hard block for a defined subset of capabilities (pattern-matched dangerous shell commands, `execute_code` in full, and anything the operator adds to `approvals.deny`) — this is not nothing, and Sprint 06 was right not to write it off. But the majority of realistic side-effecting surface a Planner would actually use — ordinary file writes, ordinary shell commands (which covers most legitimate task execution, not just the dangerous minority), and all network access — has **zero** Hermes-side lever of any kind, configured or not: no allowlist, no denylist, no mode flag reaches them, because Hermes's gate only ever triggers on a textual pattern match or a fixed sensitive-path list, never on "does JARVIS actually authorize this." This is squarely Outcome B, not A: some dangerous capabilities are genuinely restricted; other, equally side-effecting capabilities remain structurally outside any authorization path Hermes exposes.

**Planner gate: BLOCKED — unchanged from Sprint 06, now on firmer evidence.** The two unblocking paths Sprint 06 named are now more precisely scoped, not resolved: (1) tightening Hermes's own config closes the shell/`execute_code` slice for good (live-confirmed workable) but structurally cannot reach writes or network — those have no config surface to tighten; (2) scoping Planner's own autonomy to read-only/low-risk objectives, or requiring human-in-the-loop before anything that might write or reach the network, remains the only path that actually covers the gap this sprint found unclosable by configuration.

**External boundary: REQUIRED for full coverage, not required for the slice Hermes already governs.** A sandbox/process boundary is the only mechanism this sprint's evidence supports for closing the file-write and network gaps — no Hermes configuration reaches them. It is explicitly **not** required to get real governance over the shell/`execute_code` slice; that's already available today via `approvals.deny`/`unattended_mode`, unused only because the operator hasn't set it. Building a sandbox before using the free, already-available shell/`execute_code` lever would be solving the already-solved part of the problem first.

**What Sprint 07 deliberately did not do:** write any JARVIS-side capability-policy object. Investigated first, per this sprint's own charter, whether JARVIS's running server can actually configure any of the above at request/mission time — it cannot: `command_allowlist`/`approvals.deny`/`unattended_mode` are static entries in Hermes's own `config.yaml`, set by the *operator* via `hermes config set` or by hand, with no endpoint on Hermes's `api_server` HTTP contract (`POST /v1/runs`, `/v1/runs/:id/events`, `/v1/runs/:id/approval`, `/v1/runs/:id/stop` — the complete surface, per `agent-adapter.ts`) to set them per-mission or at all. A JARVIS-side object mirroring this table would have nothing real to control and nothing real backing it if JARVIS's code ever consulted it for a decision — exactly the "decorative policy layer" this sprint's own rules forbid. The operator-facing recommendation (configure `approvals.deny`/`unattended_mode` in Hermes's own `config.yaml`) is a deployment action, not a code change, and is recorded here rather than invented as application logic.
