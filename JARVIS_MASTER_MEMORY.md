# JARVIS Master Memory Capsule

Durable architectural and product decisions. This document changes rarely — only when a real decision is made, not every time code changes. For "what's actually built right now," see `JARVIS_CURRENT_STAGE.md`. For phase-by-phase status, see `JARVIS_PHASE_STATUS.md`.

## North Star

JARVIS is a persistent personal AI operating environment, not a chatbot with tools. JARVIS (this codebase) governs: identity, policy, permissions, world state, memory, events, verification, mission lifecycle. Hermes (a separate, external agent runtime) reasons, plans, and executes. Tools provide capabilities. Electron comes last — the system must stay architecturally independent of any desktop shell until the core is functionally complete.

## Module boundaries (as actually drawn in code)

- `src/server/missions` — the mission runtime: lifecycle state machine, persistence, orchestration pipeline. The orchestrator (`orchestrator.ts`) is the *only* module that drives a mission's status beyond direct user commands. `missions/tasks` (task-DAG foundation) and `missions/checkpoints` (real checkpoint records) are sub-modules with their own tables, mirroring the same repository/service split as the parent.
- `src/server/hermes` — the intelligence boundary. One `HermesAdapter` interface, three implementations (mock / generic HTTP / Hermes-Agent-specific) selected by env var at `factory.ts`. JARVIS never embeds Hermes's reasoning; it only defines the contract Hermes must speak. As of 2026-09-21, the Hermes-Agent-specific adapter (`agent-adapter.ts`) has been verified against a real, locally-running Hermes Agent (github.com/NousResearch/hermes-agent v0.21.0) — see JARVIS_CURRENT_STAGE.md for what "real" means here and how to bring that runtime up.
- `src/server/omnirouter` — model/provider routing metadata and selection *reasoning* (regex-classified objective → provider/model), not model execution itself. It gates whether a mission may run at all (no healthy provider → mission fails) and records an audit trail; it does not call any model API directly. Note: this is JARVIS's own internal routing/audit layer and is separate from the real third-party `omniroute` CLI gateway Hermes Agent is configured to route its actual model calls through — same name, different systems; do not conflate them.
- `src/server/events` — the event bus: single write path (`emitEvent`), persisted to SQLite and published to an in-process `EventEmitter`, consumed live via SSE.
- `src/server/world-state` — Phase 03's reconciliation layer, added 2026-09-21. `getWorldState()` queries all domain services (system, missions, files, spotify, schedule, weather, news, omnirouter, hermes) in parallel and wraps each in `{data, fetchedAt, knownCacheTtlMs, error}`. It does not replace `events` (the append-only history/audit log) or any domain's own service (still the source of truth, still owns its own caching) — it is a read-through aggregator only, with no caching or polling of its own. A domain failing (e.g. Spotify not connected) never fails the rest of the snapshot.
- `src/server/security` — policy (mission-creation-time) + tool-policy (execution-time gate) + audit. Deliberately fail-closed: unknown tool names are treated as high-risk `ASK`, not silently allowed; a missing tool-request handler denies by default.
- `src/server/verification` — deterministic, non-LLM verdicts. A floor, not a ceiling: it can never mistake "the model responded" for "the mission succeeded."
- `src/server/db` — the only code that touches SQL. `node:sqlite` (`DatabaseSync`), one local file, WAL mode, foreign keys on. Repository modules elsewhere are the only other code allowed to import `getDb()`.

## Standing invariants (do not silently violate these)

1. **Honesty Rule is enforced in code, not just policy.** The mock Hermes adapter labels every result `source: "mock"` and puts "MOCK HERMES — no real agent runtime connected" directly in the output text. The verifier can never return `PASS` when a mission declares zero success criteria. OmniRouter's per-model usage is always `[]` rather than a fabricated percentage when no real provider telemetry exists. Any new subsystem must follow this pattern: an honest empty/unknown state, never a plausible-looking fake one.
2. **Fail-closed on tools JARVIS actually sees.** High/critical-risk tools never auto-allow, even if pre-approved in `allowedTools`. Unrecognized tool names default to `ASK`, not `ALLOW`. No tool-request handler configured → deny. **Important caveat, confirmed by live testing 2026-09-21:** this only covers tool calls the connected Hermes runtime actually reports via a `tool.requested`/`approval.request` frame. The real Hermes Agent integration does *not* report every tool call it makes — read-only tools were observed executing with zero events reaching JARVIS at all, because Hermes Agent's own internal approval system doesn't flag them, independent of anything JARVIS's policy says. Do not describe or rely on JARVIS's tool gate as covering "everything Hermes does" — it covers "everything Hermes chooses to ask about." See JARVIS_PHASE_STATUS.md Phase 05 for the open follow-up.
3. **`emitEvent()` is the only way to create an event.** Never insert into the `events` table directly, and never mutate mission/task state without also emitting the corresponding event — the SSE stream and history replay depend on this being true for every state change.
4. **New DB tables need no migration entry; altering an existing table does.** `CREATE TABLE IF NOT EXISTS` in `SCHEMA_SQL` is sufficient for anything new. Only `ALTER TABLE` against a table that has already shipped goes in the `MIGRATIONS` array (and must tolerate re-running against a DB that already has the column).
5. **SQLite is the local single-user world-state store by design, not a placeholder.** Structured columns are JSON `TEXT` specifically so a future move to Postgres/JSONB only touches the repository layer, not services or callers.
6. **Dark theme is not a setting.** `<html className="dark">` is hardcoded in `layout.tsx` — JARVIS has one visual identity, not a light/dark toggle.
7. **Never fabricate multi-step intelligence ahead of the phase that earns it.** When a subsystem's DAG/graph/plan shape is built before the reasoning to fill it exists (e.g. the Phase 01 task model before Phase 07's planner), the code must create the minimal honest structure (e.g. exactly one root node) and say so in a comment — not synthesize fake decomposition to make the feature look more capable than it is.
8. **A budget dimension that can't be honestly enforced stays unenforced, not approximated.** `Mission.budget.maxUsd` has no real cost figure to check against anywhere in the system (Hermes Agent's `usage` object reports tokens, not `cost_usd`, on the terminal event JARVIS actually consumes) — it is accepted and stored, never checked, and this is documented, not silently ignored. Contrast with `maxTokens`, which real usage data now exists for and is genuinely enforced (post-hoc, since Hermes only reports totals at completion — see `orchestrator.ts`'s `failMissionOnBudgetViolation`).
9. **A schema-only field superseded by a real table stays as dead schema, not a second write path.** `Mission.checkpoints` (JSON column) predates `missions/checkpoints` (a real dedicated table + repository + service, added 2026-09-21, same pattern as `mission_tasks`) and is never written to by any code — the table is canonical. Do not "fix" this by writing to both; query checkpoints via `listMissionCheckpoints(missionId)`, not `mission.checkpoints`.

## Product/UI decisions

- Home Mode, Work Mode, Focus Mode, Music, System, IMA (news feed), Calendar, and Settings are sibling routes under one shared `AppShell` (sidebar + top bar) — not nested mode-switch layouts. Home is the ambient/glanceable surface; Work is the operational surface (missions, OmniRouter, tasks, focus tools).
- Visual direction: premium, restrained, dark, functional, minimal, developer-grade. No cyberpunk HUD, no giant glowing orb, no decorative graphs, no fabricated metrics. An empty/offline state (e.g. "No active missions," a provider shown OFFLINE) is correct UI, not a bug to hide.
- Frontend priority order for Work Mode (per the roadmap): Command Bar → mission creation → Mission Inspector → live SSE updates → mission controls → real event stream → real OmniRouter state → dedicated operational screens. As of this writing, all of these are implemented and wired to real backends (verified: Command Bar POSTs to `/api/missions`; OmniRouter panel reflects real provider online/offline state; missions are consumed live via SSE, not polling).

## Naming conventions worth preserving

- ID prefixes are per-domain and must not collide: `mission`, `task` (personal to-do items — unrelated to mission tasks), `mtask` (mission-task-DAG nodes), `chk` (mission checkpoints), `sched`, `audit`, `evt`.
- `src/server/tasks/` (personal to-do list) and `src/server/missions/tasks/` (mission task DAG) are deliberately separate, differently-scoped concepts that happen to share the word "task" — do not merge them or rename one to make the collision go away; the subdirectory nesting under `missions/` is what disambiguates the import path.

## Local real-infrastructure dependencies (2026-09-21)

Two real third-party processes must be running locally for JARVIS to use its real (non-mock) Hermes path — both genuinely installed on this machine, not something JARVIS's own code manages:

1. **OmniRoute gateway** (`omniroute serve`, port 20128) — the real model-routing gateway Hermes Agent calls into. Start/stop/check via the `omniroute` CLI (`serve` / `stop` / `health`). Takes ~20-25s to fully report healthy after starting — a health check run immediately after start can read as unhealthy while it's still warming up.
2. **Hermes Agent gateway** (`hermes gateway run`, port 8642) — the real agent runtime, via its `api_server` platform. Depends on (1) being up first (its configured model provider is OmniRoute). Config already set up (`hermes config set platforms.api_server.*`, `API_SERVER_KEY` in its own env file, matching `HERMES_AGENT_API_KEY` in this repo's `.env.local`) — see `.env.example` for the exact commands if it ever needs re-doing on a fresh machine.

Neither is started automatically by `npm run dev` — they are separate, standing processes. If `GET /api/hermes/health` reports `healthy: false`, check whether these are running before assuming a code regression.
