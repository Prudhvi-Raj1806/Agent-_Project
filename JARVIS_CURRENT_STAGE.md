**Charter:** close the write/shell/network Hermes-side governance gap Sprints 06/07 established (ordinary writes, ordinary shell commands, and network/web-tool calls have zero Hermes-side lever, configured or not) by building the smallest real EXTERNAL execution boundary appropriate to a Windows dev machine — no Docker/Kubernetes/custom sandbox infra. ### 1. Technology chosen, and why

Evaluated: Docker (rejected — explicitly out of scope, and the sprint's own gap is about write/shell/network governance on a system that already runs Node natively, not about environment reproducibility); Windows Job Objects for real CPU/memory/process-count limits (evaluated, NOT used this sprint — getting a real Job Object handle from Node requires either a native addon or a compiled helper process, and no maintained option was verified available/buildable this session; using one speculatively without verifying it actually enforces a limit would violate the Honesty Rule just as much as not having one); a restricted Node `child_process` + workspace path-scoping + `fs` wrapper + an executable allowlist + `taskkill /pid /t /f` for real tree-kill (CHOSEN). Rationale: this combination is verifiably real for the two properties that matter most for the identified gap — (a) a write cannot escape its assigned workspace (live-tested path traversal and symlink/junction-style escape via `resolveWithinWorkspace`'s canonicalize + realpath-verify, not a bare string compare) and (b) a runaway or malicious process is genuinely terminated on timeout or cancellation, not just abandoned (live-tested: a real spawned Node process running a 30s sleep was confirmed gone well before its own timer would have fired). It is honestly weaker than Job Objects on resource limits (no real memory/CPU ceiling) and weaker than a firewall/proxy on network isolation for spawned processes (see below) — both stated as EXTERNAL LIMITATIONS, not silently omitted.

**What this does NOT cover (EXTERNAL LIMITATION, stated plainly):**
- No real CPU/memory ceiling — only a timeout. `ResourceLimits.maxMemoryMb` is accepted, never enforced (`src/server/boundary/process-runner.ts`'s doc comment).
- No real network isolation for a spawned child process's own sockets — `network-policy.ts`'s `checkNetworkAllowed` only gates a direct fetch the boundary itself performs. A shell command that internally calls `curl`/opens sockets is NOT observed or blocked by this implementation. Concrete recommendation if this is ever needed: a mandatory local allowlisting HTTP(S) proxy (`HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY` env injection) PLUS an outbound Windows Firewall rule scoped to the boundary's spawned process tree — the proxy alone is bypassable by a process that opens raw sockets and ignores the env vars; only the firewall rule closes that case. Neither built this sprint.
- Not wired into `missions/orchestrator.ts`'s `handleToolRequest` — see the honest limitation list in JARVIS_PHASE_STATUS.md's Phase 05 Sprint 08 section for exactly why (no live Hermes write/shell/network tool-call shape was available to map against this session either, same unreachable-model-backend issue as Sprint 07) and the precise next step to close it.

### Hermes Agent's real approval architecture (read from its own installed source, not inferred)

Hermes Agent (github.com/NousResearch/hermes-agent v0.21.0, full source checkout at `C:\Users\Prudh\AppData\Local\hermes\hermes-agent\`) has **no per-tool risk/approval classification** anywhere in its tool registry (`tools/registry.py`'s `ToolEntry` carries no `risk_level`/`requires_approval`/`read_only` field). Approval is **command-string and path pattern matching**, not a generic property of a tool:

- **Shell/terminal commands** are checked against `tools/approval_detection.py`'s `DANGEROUS_PATTERNS` (~120 regexes) and `HARDLINE_PATTERNS`, via `check_all_command_guards`/`check_dangerous_command` in `tools/approval.py`. A command matching neither list — which includes `ls`/`dir`, `date`, and (per this sprint's own live test) an ordinary file write — returns `_approved()` with **zero human/gateway interaction and zero approval-related event of any kind**.
- **File writes** are approval-gated only for a specific sensitive-path allowlist (`tools/file_tools_write_guards.py`'s `is_write_approval_required`, e.g. `~/.ssh/config`) or a small configured set of "protected agent-instruction files." An ordinary path — including the dedicated temp test directory this sprint used — is not gated.
- **The `api_server` platform specifically is structurally excluded from Hermes's own interactive-approval context.** `tools/approval_context.py:134` defines `_UNATTENDED_APPROVAL_PLATFORMS = frozenset({"webhook", "msgraph_webhook", "api_server"})`; `_is_gateway_approval_context()` returns `False` for any of these. This is a **hardcoded platform classification in Hermes's own source, not a config value** — no `config.yaml` key changes it, and this sprint did not modify Hermes's installed source (out of scope, per its own rules). For api_server, a *flagged* dangerous command resolves via `approvals.unattended_mode` (`approve`/`deny`, default `deny`) entirely inside Hermes's own process — never as an SSE round-trip to JARVIS, approval-gated or otherwise.
- Real, working allowlist/denylist mechanisms exist (`command_allowlist` — permanent, glob-matched; `approvals.deny` — `fnmatch` globs, evaluated unconditionally before any auto-approve path) but **neither is present in this installation's live `config.yaml`** — both are at their permissive defaults.
- `terminal.backend: local` (this installation's live setting) means **fully unsandboxed direct host execution** — confirmed independently by Hermes's own `SECURITY.md` §2.2: *"The terminal backend... The default runs commands directly on the host."* Non-local backends (docker/singularity/modal/daytona/vercel_sandbox — all real, supported options) only sandbox the `terminal()`/file tools, never `execute_code`, MCP subprocesses, plugin loading, hook dispatch, or skill loading, which run in the bare agent process regardless of backend. Hermes's own `SECURITY.md` states its only real security boundary is the operating system, and explicitly lists "disabled approvals" and "local backend in production" as accepted operator trade-offs, not bugs — bypassing its approval/pattern system is out of scope for its own vulnerability reports.

**The single most important finding, and the one that changes this sprint's conclusion from Sprint 05's:** Hermes Agent's api_server platform emits a **second, entirely separate, unconditional event pair** for every tool call — `tool.started`/`tool.completed` — independent of whether that call was ever approval-gated. Verified directly against the raw wire, bypassing JARVIS entirely (`POST /v1/runs` + `GET /v1/runs/:id/events` straight to `http://127.0.0.1:8642`, using `HERMES_AGENT_API_KEY`):
```
data: {"event": "tool.started", "run_id": "run_fa2f...", "tool": "search_files", "preview": "*"}
data: {"event": "tool.completed", "run_id": "run_fa2f...", "tool": "search_files", "duration": 1.213, "error": false}
```
Reproduced identically for a real file write (`"tool": "write_file", "preview": "C:\\...\\rawsse2.txt"`) and a real shell command (`"tool": "terminal", "preview": "date"`) — **no `approval.request` frame appeared for any of the three**, confirming Hermes's own unattended/api_server bypass applies uniformly to read, write, and shell-command calls, not just read-only ones as Sprint 05's single test suggested.

**JARVIS's own contract already anticipated this exact event pair and had simply never wired it up for the real adapter.** `hermes/contract.ts`'s `HermesToolEventFrame` (`tool.started`/`tool.completed`/`tool.failed`), `hermes/types.ts`'s `HermesExecuteCallbacks.onToolEvent`, `missions/orchestrator.ts`'s `onToolEvent` handler (wired since at least Phase 02, emitting real `tool.started`/`tool.completed`/`tool.failed` events into JARVIS's event log), the `EventType` union, and even the mission-inspector UI's rendering of those three event types — all pre-existed this sprint, fully built and tested against `http-adapter.ts` (the generic fixture adapter). Only `hermes/agent-adapter.ts` — the one adapter that actually talks to the real Hermes Agent — never translated Hermes's real `tool.started`/`tool.completed` SSE frames into a call to `callbacks.onToolEvent`; its `stream()` switch statement silently dropped them in its `default` case alongside frame types it genuinely has no handling for.

**Fixed this sprint, using only pre-existing architecture — no new event types, no new callback, no sandbox:** `hermes/agent-adapter.ts`'s switch statement now handles `tool.started`/`tool.completed`, mapping Hermes's real fields (`tool`, `preview`, `duration`, `error`) onto JARVIS's existing `HermesToolEventFrame` shape and calling `callbacks.onToolEvent`. Hermes's wire carries no per-call id for these two frames (only `approval.request` has `request_id`); JARVIS synthesizes one (`${runId}:${toolName}:${timestamp}`) purely for its own event correlation — documented in-code as synthesized, not Hermes-reported data, consistent with the Honesty Rule. A `tool.completed` frame with `error: true` is mapped to `tool.failed`, since Hermes's wire gives no further detail on this event to preserve. **This is observation, not control:** `tool.started` does not pause Hermes the way `approval.request` does — there is no response channel, so nothing here can allow/ask/deny a call Hermes's own approval system didn't already choose to gate; it closes a visibility gap, not the governance gap.

**Verified live, end-to-end, after the fix, against the real running stack:** a fresh JARVIS mission ("list files in a dedicated temp directory, then report a marker phrase") produced this real event history for the first time —
```
... agent.started → tool.started {toolName: "search_files", input: "*"} → tool.completed {toolName: "search_files", output: {durationSeconds: 1.245}} → mission.progress ...
```
— with a real `toolCallId` correlating the pair. Test artifacts (`C:\Users\...\Temp\jarvis-sprint06-hermes-test\` and `...\jarvis-sprint06-verify\`, each holding one disposable marker/test file) were created fresh for this sprint's experiments and fully deleted afterward; the repository, `.env.local`, and the user's real files were never touched.

### Planner dependency

**BLOCKED, not partially blocked.** This sprint closed a real observation gap — JARVIS can now audit, after or concurrently with the fact, every read/write/shell tool call Hermes Agent makes via api_server. ### Security assessment (Section 16 of this sprint's brief, answered directly)

- **What can Hermes do without JARVIS?** Effectively everything an unsandboxed local coding agent can do on this machine — read/write/list files anywhere the OS user can reach, run shell commands (gated only by Hermes's own regex denylist plus a default-deny for flagged dangerous patterns), and — unverified this sprint — browse the web, execute code, and call MCP/plugin tools. None of this is gated by JARVIS's own policy unless Hermes chooses to ask.

**Goal:** close the "Phase 05 tool-gate-bypass" finding carried open since Sprint 02/03, or — if it turns out not to be closable within this sprint's own explicit constraints (no sandboxing, no Computer/Browser Control, no Hermes tool discovery) — establish that honestly, verify no *other* JARVIS-controlled side effect bypasses policy/permission, and harden the existing boundary's tests, secret handling, and audit integrity instead.

The honest call is to leave it open, document it precisely (as this section does), and not claim a guarantee the code doesn't provide.

**What was verified and hardened instead, all within this sprint's actual scope:**

1. **Fail-closed made explicit, not incidental, at the one governed gate (Section 10).** `tools/executor.ts`'s `evaluateGovernedToolCall` — the single place both Quick Actions (`executeTool`) and Hermes-mediated calls (`orchestrator.ts`'s `handleToolRequest`) reach `security/tool-policy.ts`'s `evaluateToolRequest` — now wraps that call in a `try/catch`. Before this sprint, if `evaluateToolRequest` ever threw (a malformed request shape — e.g. a missing `forbiddenActions` array — or any unexpected internal error), the exception happened to still prevent execution (nothing past the throw could run), but produced **no audit row and no defined verdict** for the caller to act on: an accidental side effect of control flow, not a designed property. It now converts any such failure into an explicit, audited `DENY` (`risk: "critical"`, reason: "Security policy evaluation failed — denying by default"), logged via `logger.error("tool.policy.evaluation_failed", ...)`. Verified with a real malformed-input case (a request object missing `forbiddenActions`, which genuinely throws inside `evaluateToolRequest`'s `.includes()` call), not just a mocked throw — see `tools/executor.test.ts`.
2. **The single-call-site invariant now has a repository-wide, structural regression test (Section 16), not just a behavioral one scoped to `orchestrator.ts`.** `missions/tool-request-boundary.test.ts` (Sprint 02) already proves, behaviorally, that `orchestrator.ts` doesn't call `evaluateToolRequest` directly. New this sprint: `security/governed-boundary.test.ts` scans every `.ts`/`.tsx` file under `src/` and fails if `evaluateToolRequest` is imported by name from anywhere in **non-test application code** other than `tools/executor.ts` (the governed gate) or `tools/registry.ts` (a single, explicitly-documented, metadata-only read of a tool's `risk` classification — never a gate, never an execution decision; see standing invariant discussion in JARVIS_MASTER_MEMORY.md). This is deliberately structural rather than behavioral, per the sprint's own Section 16 guidance ("only use structural/source inspection if there is genuinely no better test") — proving "there is no other caller anywhere in the repository" is not something any single module's mock/spy can establish; only a repo-wide scan can.
3. **Audit append-only is now DB-enforced, not just an application convention (Section 13).** `db/schema.ts` adds two `CREATE TRIGGER IF NOT EXISTS` statements (`audit_events_no_update`, `audit_events_no_delete`) that `RAISE(ABORT, ...)` on any `UPDATE`/`DELETE` against `audit_events`. Verified with a direct SQL `UPDATE`/`DELETE` against the table, bypassing `recordAudit` entirely (`security/audit.test.ts`), confirming the row is genuinely unmodifiable through this database handle — not merely that no application code happens to attempt it. Stated honestly, not oversold: this does not make the log cryptographically tamper-evident (raw filesystem access to the `.sqlite` file, or a future migration that drops the triggers, could still alter it) — it closes the ordinary application-code path, which is what "append-only by convention" actually meant before this sprint and is now a real, enforced guarantee for that path.
4. **Secret redaction is now value-based as well as field-name-based (Section 12).** The prior audit's finding — "logger redaction is field-name based rather than value-based" — is real and unchanged in the old code: a secret value logged under an innocuous key (or embedded as a substring inside a longer string, e.g. an error message that happens to include a token) passed through untouched. `logging/logger.ts` now also scans every logged string for exact occurrences of any currently-configured secret from a fixed, known list of secret-shaped env vars this codebase actually reads (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `DEEPSEEK_API_KEY`, `OMNIROUTE_API_KEY`, `HERMES_AGENT_API_KEY`, `ELEVENLABS_API_KEY`, `JARVIS_VOICE_PASSCODE`, `SPOTIFY_CLIENT_SECRET` — the same set `.env.example` documents), and redacts any occurrence regardless of field name. Deliberately a fixed known-name list, not a generic "redact every env var" scan (which would be slower and would redact ordinary non-secret configuration by accident), and deliberately skips values under 8 characters (too short to usefully identify as a real secret, too likely to false-positive on ordinary short strings). Values are re-read from `process.env` on every log call rather than cached at module load, so both `vi.stubEnv` in tests and a real runtime env change take effect immediately. Six new tests in `logging/logger.test.ts` cover: redaction under an unrelated field name, redaction as a substring of a larger string, the pre-existing field-name pass still working independently, no false-positive redaction of ordinary short strings, an empty/unset secret never being treated as a value to redact, and redaction inside nested arrays/objects.

Flagged here as a real, pre-existing architectural fact worth a future owner decision (bring media controls into the Tool Registry the same way Quick Actions were, if Hermes ever gains the ability to control media), not invented as a new vulnerability and not fixed as part of this sprint.

**What this sprint deliberately did not touch, per its own scope (Section 17):** Planner/Replanner, semantic verification, automatic retries, rollback, Agent Autopsy, Computer Control, Browser Control, Hermes tool discovery, a full secret vault, a distributed policy/authorization service, or any sandboxing/process-boundary system for Hermes Agent (the one thing that *would* actually close the Phase 05 gap — see above).

## Production Sprint 03 — Verification v2 + Safe Recovery Foundations (2026-09-21)

**Goal:** close the gap Phase 06's own status had named for weeks — "Hermes execution success" and "verified mission success" were conflated at the one place that actually decides a mission's fate — plus lay minimal, honest foundations for failure classification and execution identity, without building retries, recovery, a planner, or an LLM verifier (all explicitly out of scope this sprint).

**The bug, found by reading the code, not by a failing test:** `missions/orchestrator.ts`'s final block used to read `if (verdict.verdict === "FAIL") { ...FAILED... } else { ...COMPLETED... }`. A genuinely `UNCERTAIN` verdict — Hermes reported success, but there was insufficient evidence to call the mission verified — fell into the `else` branch and reached `COMPLETED`, exactly like a real `PASS`. Visible in this session's own earlier test logs all along: `"verification.completed", "status":"uncertain"` immediately followed by `"mission.completed"`. Not a new regression — present since the verifier itself was built — but never previously named as a defect until this sprint's own framing made it explicit.

**The fix:** `src/server/missions/completion-policy.ts` — a new, small, pure `decideMissionCompletion(verdict, hasSuccessCriteria)`, the one function now allowed to decide COMPLETED vs. FAILED from a `VerificationResult`. Rule: `FAIL` → `FAILED`. `UNCERTAIN` with success criteria declared → `FAILED` (verification was explicitly requested and came back inconclusive — must not be treated as verified). `UNCERTAIN` with no criteria declared → `COMPLETED` (the one deliberate, documented exception: a mission that never asked to be verified never failed to verify — preserves every pre-existing test and every mission with no verifiable postcondition, per this sprint's own instruction not to force verification onto missions that never asked for it). The stored `VerificationResult.verdict` always still says `UNCERTAIN` in that exempted case — it is never rewritten to `PASS`; only the coarser mission-level outcome is `COMPLETED`, for a documented reason.

**Tool-level execution/verification separation, and one real postcondition (Section 6/7):** `src/server/tools/verification.ts`'s `verifyToolOutcome(tool, result)` runs a tool's own declared `verify` function, if it has one — deliberately kept outside `tools/executor.ts` (ToolExecutor stays execution-only, per this sprint's explicit rule). A tool with no `verify` (every Quick Action except two) gets `null` back rather than a `VerificationResult` fabricated from its bare self-report — the whole point being that a self-report and an independent observation must never be indistinguishable to a caller. `take-notes` and `take-screenshot` (`actions/registry.ts`) now declare `verificationStrategy: "file-exists"` and a real `verify` function using `node:fs/promises`'s `access` — genuinely checking the file each action is supposed to produce actually exists, not trusting the shell command's exit code alone. `take-screenshot`'s check uses the exact path the action itself reported; no path reported → `UNCERTAIN`, never guessed. Wired into `actions/service.ts`'s `runQuickAction`, which now calls `verifyToolOutcome` after a successful `executeTool`, skipped entirely for a blocked/unknown action (404/403 — nothing executed, nothing to observe).

**Deliberately not wired into production — a documented, reasoned exception, not an oversight:** the architecture's own example (`OPEN_APP Spotify` → check the process exists) implies process-existence observation for `open-vscode`/`open-obsidian`/`welcome-routine`. Not built this sprint: `systeminformation`'s process-listing call has no benchmark proving it's fast on this hardware (the 2026-09-20 perf sprint found several of its other calls taking 1-4s, WMI-backed), and using it as a synchronous per-action check risks exactly the "repeated system scans" pattern this sprint's own rules forbid without evidence it's safe. Filesystem checks carry no such risk, which is why they — not process checks — became the real production postcondition.

**Failure classification (Section 8):** `src/server/verification/classification.ts` — `TRANSIENT | PERMANENT | POLICY_DENIED | PERMISSION_DENIED | VERIFICATION_FAILED | VERIFICATION_UNCERTAIN | UNKNOWN`. Every classifier prefers `UNKNOWN` over an invented category: "no healthy provider" and "Hermes runtime unreachable" are both `UNKNOWN` (the evidence doesn't distinguish transient from permanent). Real signals used where they exist: `HermesError.retryable` → `TRANSIENT`/`PERMANENT` (the catch-block failure in `executePipeline`); a tool-policy `DENY` or a budget violation → `POLICY_DENIED`; a missing/invalid voice-verification token in `tools/executor.ts` → `PERMISSION_DENIED`, now genuinely distinguished from a blanket policy `DENY` (both used to return an identical-shaped 403 with no classification at all); a verification `FAIL`/`UNCERTAIN` → `VERIFICATION_FAILED`/`VERIFICATION_UNCERTAIN`. Attached as metadata on `mission.failed` events and on `ToolExecutionOutcome` — no new logging system, and nothing anywhere retries automatically based on it. It exists to be *usable later* by a future Planner/Replanner (Phase 07), not consumed by one yet.

**Execution identity (Section 9):** `src/server/verification/execution-identity.ts` — `executionIdentityKey({missionId, taskId, toolCallId})`, built entirely from IDs that already exist. No new database, no suppression/dedup logic anywhere — tested only for determinism and non-collision. Attached to the tool-call budget-violation event (`request.toolCallId` is naturally available there) and to `pauseMission`'s checkpoint state (mission-scoped, `taskId`/`toolCallId` both `null`).

**Checkpoint integration (Section 10):** `pauseMission`'s existing checkpoint (unchanged mechanism, no second one built) now also captures `mission.verification` (the mission's last known verification result, `null` if it's never completed a run) and its `executionIdentity` key, alongside the fields it already captured (`status`, `progress`, `currentObjective`, `agents`).

**`VerificationResult` extended, minimally, backward-compatibly:** added one optional field, `strategy?: "text-match" | "self-reported" | "file-exists"`, so a result is never just an opaque verdict with no record of what kind of check produced it. Optional specifically so every pre-Sprint-03 call site (and every existing test asserting on `.verdict`/`.reasons`) remains valid untouched; `verifier.ts`'s four return points now all tag `strategy: "text-match"`.

**Repository audit performed (Section 17):** grepped for every `"COMPLETED"` mission-status write (`orchestrator.ts:756`, the only real call site, gated by `decideMissionCompletion`), every direct `tool.execute()` call (`tools/executor.ts:109`, the only one — ToolExecutor remains the single execution boundary), every `createCheckpoint`/`verify`/`verifyToolOutcome`/classification/execution-identity call site (each exactly where designed, no duplicates), and confirmed the dormant `verifications` SQLite table is still touched by zero application code (unchanged from the Sprint 02-era baseline — not newly built on, not newly ignored, same honest dormancy as before).

**Goal:** close the one gap Production Sprint 01 left open and documented — `missions/orchestrator.ts`'s `handleToolRequest` (the gate for every Hermes-mediated tool call) still called `security/tool-policy.ts`'s `evaluateToolRequest` and `security/audit.ts`'s `recordAudit` directly, independently of `tools/executor.ts`'s `executeTool` (Quick Actions' equivalent path) — two call sites reaching one shared policy table, not one call site reaching one boundary.

**What changed:**
- `src/server/tools/executor.ts` — added `evaluateGovernedToolCall(request, auditTarget)` and `recordToolCallResolution(auditTarget, approved, reason)`. `evaluateGovernedToolCall` calls `evaluateToolRequest` and, for an immediate ALLOW or DENY verdict, audits it; it returns an ASK verdict unaudited, since an ASK's approval/denial is a separate step with its own actor. `recordToolCallResolution` audits that later resolution. `executeTool` (Quick Actions) was refactored to call these instead of inlining `evaluateToolRequest`/`recordAudit` itself — no behavior change, same audit rows (`resourceType: "tool"`, `resourceId: <action id>`).
- `src/server/missions/orchestrator.ts` — `handleToolRequest` now calls `evaluateGovernedToolCall`/`recordToolCallResolution` instead of `evaluateToolRequest`/`recordAudit` directly. Audit rows are unchanged (`resourceType: "tool_call"`, `resourceId: <toolCallId>`, same actor logic: `system` for automatic ALLOW/DENY, `owner` for a human-resolved ASK approval, `system` for an ASK auto-denied by abort). Mission-specific logic — the `WAITING_USER` pause/resume, the pending-approval promise/abort-listener plumbing, all `emitEvent` calls — stayed in the orchestrator, deliberately not moved into `tools/executor.ts` (mission state is not the executor's responsibility, per this sprint's own scope limits).
- No change to `HermesAdapter`, `factory.ts`, or any of the three adapters (mock/http/agent) — Hermes still reports tool calls via `onToolRequest`, exactly as before; only what JARVIS does with that callback internally changed.

**Verified — the boundary actually moved, not just refactored to look like it did:** `src/server/missions/tool-request-boundary.test.ts` (2 new tests) mocks `@/server/tools/executor` out entirely and wraps the real `@/server/security/tool-policy`'s `evaluateToolRequest` as a spy. It drives a real mission through a gated HTTP fixture (same technique as `tool-approval.test.ts`) and asserts (a) the mocked `evaluateGovernedToolCall` was called with the real request shape (`toolName`, `allowedTools`, `forbiddenActions`, and the audit target), for both an ALLOW and a DENY verdict, and (b) the real `evaluateToolRequest` was never called — which would only be false if `orchestrator.ts` still (or again) called `tool-policy.ts` directly. `src/server/tools/executor.test.ts` (5 new tests) covers `evaluateGovernedToolCall`/`recordToolCallResolution` directly: ALLOW and DENY audit immediately with the right shape, ASK returns unaudited, and a later resolution (approved or denied) is audited correctly.

**Section 7 investigated (Hermes tool visibility) — no code change, a documented finding instead:** Hermes receives no tool list from JARVIS at all today, not a hardcoded or incomplete one. `mission.allowedTools`/`forbiddenActions` default to `[]` and are only ever populated by whatever a mission-creation API caller explicitly passes — no UI lets an owner pick from a list (`mission-inspector.tsx` only displays these arrays, never edits them), and the real `HermesAgentAdapter.execute()` doesn't forward `allowedTools` to Hermes Agent at all (only the fixture-only `HermesHttpAdapter` includes it in its submit payload). Since there's no static/incomplete list to correct, and building tool-visibility plumbing where none exists would be exactly the "huge dynamic tool-discovery system" this sprint was told not to build, this is documented as a finding (see `JARVIS_PHASE_STATUS.md` Phase 04), not fixed.

**What this sprint deliberately did not touch (per its own scope):** the still-open, separate gap from Phase 02/05 — Hermes Agent's own internal approval system doesn't flag every tool call (read-only tools were observed executing with zero `approval.request` events reaching JARVIS at all) — is untouched. That is a limitation of what the real Hermes Agent runtime chooses to report to JARVIS, upstream of JARVIS's gate entirely; this sprint closed a duplicate-call-site problem inside JARVIS's own code, not Hermes Agent's self-reporting completeness. Both are real, but they are different problems — do not conflate "JARVIS has one governed path to its policy table" (now true) with "JARVIS sees every tool call Hermes Agent makes" (still not true, see Phase 05).

## Production Sprint 01 — Mission Integrity + Unified Tool Boundary (2026-09-21)

Three objectives: preserve prior uncommitted work, fix the pause/resume stale-execution race, and eliminate the Quick Actions policy/audit bypass. A Tool Registry initial slice was added afterward since Steps 1–3 landed clean.

**1. Pause/resume stale-execution race — fixed.** `src/server/missions/orchestrator.ts` now gives every pipeline execution (`beginMission`/`resumeMission` → `executePipeline`) a run-generation number. A run may only mutate mission/task state while its generation is still current; `pauseMission`/`cancelMission` invalidate the current generation outright, and starting a new run (a resume) implicitly supersedes whatever generation came before. Checked at every point a stale run's own adapter call could otherwise resolve and mutate state: the health check, the tool-request gate (`handleToolRequest`), the main `adapter.execute()` resolution (both success and error paths — the success path previously had **no** staleness check at all, which was the actual hole), and the post-tool-approval resume-to-`RUNNING` transition. Deliberately does not rely on `AbortSignal.aborted` alone, since an adapter that doesn't turn abort into a prompt rejection could still resolve successfully after being superseded — this is exactly the scenario the regression test reproduces (a fake `HermesAdapter` that settles `execute()` manually and never even looks at its abort signal). Verified the test is real, not a tautology, by temporarily removing the new guard and confirming the test then fails (the stale run's output really did overwrite the newer run's mission state) before restoring it.

**2. Quick Actions policy/audit bypass — fixed.** `src/app/api/actions/[id]/run/route.ts` used to call `ACTION_REGISTRY[id].run()` directly — a second execution path next to the mission pipeline's tool gate, with only a hardcoded `action.risk === "risky"` check gating one action via a voice-verification token. Every Quick Action id is now a `toolName` inside `security/tool-policy.ts`'s shared `DEFAULT_TOOL_RULES` (7 new entries added — the same table Hermes tool calls use), evaluated by the same `evaluateToolRequest` before execution. DENY blocks execution outright; ASK requires the pre-existing voice-verification token (now driven by the policy verdict, not the action's own hardcoded field) before it may run; every decision is recorded via `recordAudit`. The route is now a thin wrapper around `src/server/actions/service.ts`'s `runQuickAction`, itself a thin wrapper around the new Tool Registry's `executeTool` (see item 4).

**3. Direct model-provider bypass — fixed.** `src/server/actions/registry.ts`'s `summarize-clipboard` action used to `fetch("https://api.anthropic.com/v1/messages")` directly, with a hardcoded (and by now stale) model id. It now calls `selectModel()` (OmniRouter's existing routing decision) and then `src/server/providers/completion.ts`'s new `runProviderCompletion(routing, prompt)` — the one place a one-shot text completion is actually executed against a provider's API. Only Anthropic has a real implementation (moved from the action, not duplicated); every other OmniRouter-seeded provider (OpenAI, DeepSeek, OmniRoute) honestly reports "not implemented" rather than fabricating a result, per the Honesty Rule. `ANTHROPIC_MODEL_IDS` also fixes a real staleness bug found while doing this: OmniRouter's internal `claude-opus`/`claude-sonnet`/`claude-haiku` seed ids were never real Anthropic API model strings, and the action's own hardcoded model (`claude-3-5-sonnet-20241022`) was already outdated.

Not a leak (both clean up correctly on unmount/id-change, matching the 2026-09-20 audit's finding). No safe, small fix exists without either (a) redesigning SSE consumption to share one connection across both hooks (explicitly out of scope — "do not redesign SSE globally in this sprint") or (b) collapsing the two hooks' genuinely different needs (a lightly-patched `Mission[]` list vs. a full raw event timeline + repeated full-mission refetches) in a way that risks introducing a subtler bug into a currently leak-free system. ## Performance stabilization sprint (2026-09-20)

**Trigger:** user-reported "running JARVIS makes the laptop extremely slow," RAM spikes, and slow screen renders.

**Method:** measured before guessing. Started the real dev server, timed every route with `curl`, benchmarked each `systeminformation` call in isolation, and inspected live Windows process memory (`Get-CimInstance Win32_Process`).

**Root cause found and fixed — uncached, over-fetching system telemetry (highest-confidence, fully measured):**
`src/server/system/service.ts` (`getSystemSnapshot` / `getSystemDetailSnapshot`, used by Home, Work, and the System page — the latter polled client-side) called into the `systeminformation` package with **zero caching**, on every request. Individually benchmarked on this machine: `si.graphics()` ~3.5s, `si.networkStats()` ~4.1s, `si.osInfo()` ~2s, `si.battery()` ~1.4s, `si.cpuTemperature()` ~1s — several backed by Windows WMI queries that spawn child processes. Worse, the code called `si.networkStats()` **twice**, blocking on an extra artificial 200ms sleep in between, every single call.
Measured impact before the fix: `GET /` (Home) logged real request times of **28s and 98s** during normal use; a direct, uncontended `curl` to `/api/system` took **8–20s per call**. The System page polled this same expensive path every 3 seconds — a genuine unbounded resource-consumption pattern, not just a slow page.
**Fix:** added a shared in-flight-dedupe + 5s-TTL cache (`cached()` helper in `service.ts`) around both snapshot functions, so concurrent requests (a page load racing a poll, multiple tabs) share one real `systeminformation` pass instead of each triggering their own. Also removed the redundant second `networkStats()` call + sleep — network throughput now derives from the natural spacing between cached snapshots (first sample in a fresh process honestly reports `null`, matching the project's honesty rule, and is accurate from the second sample on). Bumped the System page's client poll interval from 3s → 5s to match the cache TTL (no benefit polling faster than the cache refreshes).
**Result:** `GET /api/system` — cold call ~9s (the real, now-unavoidable floor for a first WMI pass on this machine), cached calls **8ms** (down from 8–20s). `GET /` (Home) — cold ~5.8s, warm **79ms** (down from up to 98s). Verified concurrent-request dedupe directly: 3 simultaneous requests after cache expiry took ~8.3s total (one real pass), not 3×.
**Regression tests added:** `src/server/system/service.test.ts` (7 tests) — cache reuse across repeated calls, in-flight dedupe under concurrency, TTL expiry triggering a real refresh, single (not double) `networkStats()` call, correct null-then-real network-throughput sequencing, and that `getSystemSnapshot`/`getSystemDetailSnapshot` share one network warm-up flag.

**Other findings from the audit (no fix needed — architecture already sound):**
- `AppShell` (providers for Spotify + clap-wake) lives in `layout.tsx`, so it mounts once and persists across all route navigation — not remounted per page. No duplicate global providers found.
- Mission SSE (`useLiveMissions`) opens one `EventSource` per *active* mission, keyed on the set of active mission IDs (not on every field update), and closes all of them on unmount/id-set-change. No leak, no duplication.
- The server-side event bus (`src/server/events/bus.ts`) is a single process-wide `EventEmitter` with `setMaxListeners(200)`; each SSE route subscribes/unsubscribes cleanly on request abort.
- `useSpotifyPlayer()` (5s poll) is called independently by three components (`NowPlayingPanel`, `FocusMusicPanel`, `MusicView`), but since each lives on a different route and Next.js App Router unmounts page-level components on navigation, only one is ever polling at a time in practice — not a real duplicate-polling bug today. Worth revisiting only if a future screen renders more than one of these simultaneously.
- The clap-wake detector's mic/RAF loop is opt-in (off by default, per-user `localStorage` toggle) and fully torn down (`cancelAnimationFrame`, `AudioContext.close()`, mic tracks stopped) when disabled or unmounted.
- Client-side JS heap does not grow across repeated navigation (measured via `performance.memory` — see Build/test health above) — no evidence of a client-side render/listener leak.
- **Environment note, out of this repo's scope:** at audit time, several *unrelated* projects' dev processes (`Spotameet`, `omniroute`) were found running duplicated/orphaned `tsx watch` chains and a `--max-old-space-size=4096` server, together holding roughly 1GB+ RSS and occupying port 3000 (JARVIS's own dev server had to auto-select a different port). This is real machine load contributing to "the laptop is slow" but is not JARVIS code — flagged for the user to clean up manually, not touched by this sprint. (Note, 2026-09-21: `omniroute` is now deliberately running again, this time on purpose — see the Real Hermes section above.)

**Remaining/deferred:** the ~5-9s *cold* cost (cache miss after a 5s idle gap) is a real floor on this hardware and could be hidden further with a background stale-while-revalidate refresh — deliberately not added, since a perpetual background timer would reintroduce always-on polling/child-process cost even while the app isn't being viewed, trading one resource problem for another. Revisit only if cold hits are reported as still noticeable in practice.

## Known gaps / honest limitations carried forward

- ~~A mission with a paused-then-resumed stale pipeline run can, in a narrow race, have its old run's terminal write land after a new resumed run has taken over~~ — **fixed 2026-09-21, Production Sprint 01** (run-generation guard in `orchestrator.ts`; see that section above).
- ~~Quick Actions bypass the security policy/audit boundary~~ — **fixed 2026-09-21, Production Sprint 01** (see that section above).
- ~~`summarize-clipboard` calls the Anthropic API directly~~ — **fixed 2026-09-21, Production Sprint 01** (see that section above).
- Two SSE connections open to the same mission when an active mission is both listed and being inspected (`useLiveMissions` + `MissionInspector`) — investigated 2026-09-21, not a leak, no safe small fix found; documented for the next performance sprint (see Production Sprint 01 section above).
- Tool-approval waits (`WAITING_USER`) do not change the mirrored task's status — it stays `"running"` through the wait. Documented as intentional scope-limiting, not an oversight.
- `budget.maxUsd` is the only budget field left honestly unenforced — no cost figure exists anywhere in the system to check it against.
- All budget accounting is in-memory only (`budgetState` in `orchestrator.ts`), like the pre-existing `controllers` map — it does not survive a process restart.
- The repetition detector compares tool input by `JSON.stringify` structural equality, not semantic equality — a documented heuristic, not a guarantee.
- **(Security-relevant, most important gap — still open, re-investigated and reconfirmed 2026-09-21, Production Sprint 04)** JARVIS's execution-time tool gate only sees Hermes tool calls Hermes Agent chooses to report via an `approval.request` frame. Live-verified (2026-09-21, earlier session) that read-only tools (file listing) execute without ever emitting one — JARVIS never gets a chance to allow/ask/deny them. Whether write/delete/execute-class tools behave differently is unknown and wasn't tested live (real side-effect risk). This is a *Hermes-mediated* tool-call gap, distinct from (and not addressed by) the Quick Actions fix above — Quick Actions are owner-invoked directly, never Hermes-mediated, so they were never exposed to this particular gap. Production Sprint 04 re-inspected `hermes/agent-adapter.ts`'s `stream()` method and confirmed the code is unchanged: `onToolRequest` is only ever invoked from the `"approval.request"` case, so there is no path in JARVIS's own code to intercept a call Hermes Agent doesn't report. **Not closable by changing JARVIS's own execution boundary** — Hermes Agent's own runtime decides what to tell JARVIS about; genuinely closing this requires either Hermes Agent itself reporting more, or JARVIS sandboxing/wrapping the Hermes Agent process independently of its self-reporting (a process-boundary system explicitly out of scope for Sprint 04 — see that sprint's section above). Until resolved, do not treat JARVIS's tool gate as covering everything a real Hermes Agent mission can do — it covers everything Hermes Agent *asks about*.
- ~~The Tool Registry (`src/server/tools/`) only covers Quick Actions today — Hermes's own tool calls still go directly through `security/tool-policy.ts`, bypassing the registry.~~ — **fixed 2026-09-21, Production Sprint 02**: Hermes-mediated tool calls now reach `security/tool-policy.ts` only through `tools/executor.ts`'s `evaluateGovernedToolCall`, the same primitive Quick Actions use (see that sprint's section above). The registry (`ToolDefinition` entries with a local `execute()`) itself still only covers Quick Actions, and always will — Hermes's tools are executed by Hermes's own runtime, not JARVIS, so they were never candidates for a local registry entry in the first place. Don't conflate "the registry only lists Quick Actions" (true, by design) with "Hermes tool calls bypass governance" (no longer true).
- The execution-time tool gate still cannot see every tool call the real Hermes Agent makes — Hermes Agent's own internal approval system doesn't flag every tool category (see the item below). This is a different, still-open problem from the one just fixed above: Production Sprint 02 closed a duplicate-call-site issue inside JARVIS's own code; it did not and could not change what Hermes Agent chooses to report.
- The OmniRoute gateway and Hermes Agent gateway are standing local processes this session started, not something `npm run dev` manages — see JARVIS_MASTER_MEMORY.md. If a future session finds `/api/hermes/health` unhealthy again, check whether these are still running before assuming a regression.
- World State has no caching or polling of its own by design (see the dedicated section above) — a very chatty caller could still trigger a lot of underlying work if it calls `getWorldState()` far more often than each domain's own cache TTL; nothing currently does, but nothing throttles a future caller either.
- Spotify playback controls (`/api/spotify/play`/`pause`/`next`/`previous`/`volume`/`seek`/`transfer`) are real external side effects not registered in `security/tool-policy.ts` and not routed through `tools/executor.ts` — found during Production Sprint 04's repository-wide audit, documented rather than fixed (see that sprint's section above: no agentic/Hermes-reachable path to them exists today, so they sit outside this sprint's chartered invariant, unlike Quick Actions). Worth a deliberate decision, not an accident, if Hermes ever gains the ability to control media.
- Audit append-only is now DB-enforced (SQLite triggers, Production Sprint 04) for the ordinary application-code path, but this is not cryptographic tamper-evidence — raw filesystem access to the `.sqlite` file, or a future migration dropping the triggers, could still alter historical rows. Stated precisely, not oversold.
